## 2. 왜 이 조합인가 (문제 → 해결 매핑)

2026-11-17 육안 FAIL의 원인은 "모델이 좋아서"가 아니라 **구도와 인물 배치가 컷마다 달라졌기 때문**이다.
D66 ①(정면 카드)은 얼굴 정보는 고정했지만 **어디에 서 있는지, 카메라가 어디 있는지**는 여전히 프롬프트에 맡겨져 있었다.

| 실패 양상 | 기존 대응 | 한계 | 3D 가이드 해결 |
|---|---|---|---|
| 얼굴이 바뀜 | D66 ① 정면 카드 IPAdapter | 얼굴은 고정, 자세/구도는 자유 | 카드(정체성) + 3D 블록아웃(구도) 동시 주입 |
| 인물/배경 통일성 없음 | bible 앵커 텍스트 | 텍스트라 위치가 매번 달라짐 | 같은 3D 좌표계에 인물·건물·카메라를 배치 |
| 클립 끝 이탈(MAE 37~49) | D65 체이닝 | 시작점만 고정, 이후 드리프트 | 카메라 경로가 결정론적이라 목표 구도가 고정 |
| 원경/뒷모습 오판 | 중앙 40% 측정 | 측정일 뿐 생성은 그대로 | heading(앞/뒤)·거리(wide/close)를 3D 명세에 명시 |

## 3. 채택 아키텍처 — "3D 가이드 → 실사 레이어"

```
입력(레퍼런스/첫 프레임/텍스트/목소리)
        │
        ▼
  [신규] Scene3D 빌더  ── 결정론적 3D 배치
        │  · card: 정면 카드(D66 ①) → 인물 정체성
        │  · visual/motion → 카메라 거리·heading·소품 배치
        ▼
  [신규] 레이아웃 패스 → layouts/layout_NN.png (D70: Blender 3D 렌더)
        │  · 기본 백엔드 = Blender 4.5.16 LTS headless (같은 Scene3D를 실제 3D로 렌더)
        │  · CINEMOKHWA_LAYOUT_BACKEND=cpu 로 기존 numpy+PIL 블록아웃도 선택 가능
        │  · 실측 라플라시안: Blender 5~15 vs CPU 445 → 실사 잠재 번짐 구조적 해소
        ▼
  [기존] SDXL 키프레임  =  IPAdapter(정면 카드) + img2img(레이아웃)  ← D67 핵심
        ▼
  [기존] Wan I2V  =  같은 shot은 앞 프레임 체이닝(D65)
        ▼
  [기존] FFmpeg CRF16 조립 → final.mp4
```

### 결정 D67 (3D 레이아웃 패스)
- 대본의 `anchors`/`visual`/`motion`에서 **결정론적으로** `Scene3D`(카메라·인물·배경 블록)를 만든다.
- 레이아웃 PNG는 `work/<run>/layouts/layout_NN.png`에 저장하고 캐시키에 포함한다.
- 원래 numpy+PIL 소프트웨어 렌더로 구현했으나, D70에서 Blender가 **기본 백엔드**가 됨(아래 참조).

### 결정 D68 (실사 레이어 = 기존 자산 재사용)
- 인물 정체성: D66 ① 정면 카드를 IPAdapter로 주입(그대로).
- 구도/원근: 레이아웃 PNG를 img2img 잠재로 주입(신규). 두 참조를 **동시에** 사용.
- 영상화: Wan I2V 20스텝, 같은 shot 체이닝(그대로). 새 모델·유료 API 없음.

### 결정 D69 (정교 3D 모델링 — 보류, Q9 조사 완료)
- **Hunyuan3D 2.1**: 커뮤니티 라이선스가 **대한민국을 지역에서 제외** → 이 프로젝트에서 사용 불가.
- **TRELLIS.2**: 모델·코드는 MIT지만 렌더 의존성 `nvdiffrast`/`nvdiffrec`가 별도(비상업) 라이선스 + README상 24GB VRAM/Linux 요구 → 보류.
- Q9는 "해소 전 설치 금지"가 아니라 **조사 완료 후 부적합 판정**으로 종결. `export_blender()`로 자산 교체 경로만 마련해 두고 고퀄리티 모델링은 보류.

### 결정 D71/D71b (밝기 일관성 — guided-40 실측에서 발견)
- **증상**: guided-40은 개별 클립 verify 전부 PASS였지만 씬 간 Yavg가 34/35/116(차이 81.97).
  사용자의 원래 불만("1·2 밝고 3 어두워 다른 공간 같다")이 뒤집힌 형태로 재발.
- **원인 1 (검증 공백)**: verify는 컷 내 `yavg_std`만 보고 **씬 간 평균 밝기 차이를 안 봤다.**
  → `CROSS_YAVG_WARN=25`, `CROSS_YAVG_FAIL=50` 추가, 종합 판정에 반영(D71).
- **원인 2 (지표 편향)**: 키프레임 4시드 선택이 `center_sharpness`(라플라시안 분산) 최고만 골랐다.
  어두운 이미지는 국소 대비가 커서 lap이 인위적으로 높다. guided-40 scene 1 실측:
  정상 Y112/lap52 후보가 **암부 Y35/lap174**에 밀려 탈락. 상대 비율(최고의 60%)로도
  정상 후보가 걸러져 D71b에서 **절대 하한 `MIN_CENTER_SHARPNESS=40`**으로 변경.
  → "충분히 선명한 후보 중 목표 밝기(105)에 가장 가까운 시드" 선택.

### 결정 D72 (motion-aware 밝기 안정 — guided-50scene 2 실측)
- **증상**: D71b 수정 후 guided-50의 씬 간 밝기 차이는 8.49(PASS)로 해결됐지만,
  scene 2의 컷 내 `yavg_std=5.459 > YAVG_STD_PASS=5.0`로 FAIL이 남았다.
- **궤적 분석**: scene 2 밝기는 104→125→109의 단일 완만 아치. 1차 미분/표준편차가
  **0.350**으로, 오히려 PASS된 scene 1(0.398)·scene 3(0.455)보다 낮았다.
  → 고주파 깜빡임이 아니라 카메라가 조명을 지나가며 밝아졌다 어두워진 자연스러운 변화.
- **판정 변경**: `yavg_std`만 보던 것을 `yavg_step_ratio = mean|ΔY|/std`를 함께 본다.
  - `std < 5` → PASS (기존)
  - `std < 12` **and** `step_ratio < 0.75` → PASS (완만 아치, D72)
  - `std >= 12` → FAIL (아치여도 시각적으로 과한 스윙)
  - 나머지 → 기존 wide WARN / FAIL 유지 (고주파 깜빡임은 계속 FAIL)
- **결과**: guided-50 종합 **FAIL → WARN**. 씬 간 밝기 8.49 PASS, 드리프트 WARN(연장 씬 카메라 이동)만 남음.
  WARN은 숫자 PASS만으로 통과시키지 않는 원칙에 따라 유지하고 육안 확인 대상으로 표시.

### 결정 D70 (Blender 채택 — 2026-11-21 설치 완료)
- **Blender vs Unity 비교**: Blender = 무료 GPL, 오프라인 렌더(Cycles/EEVEE), Python 자동화, 정적 구도 도면에 최적.
  Unity = 실시간 게임 엔진이라 이 파이프라인에는 과하고 유료 티어 필요 → **Blender 채택**.
- 설치: Blender **4.5.16 LTS** Portable(공식 ZIP 398MB) → `C:\Users\mbc\mokhwa\apps\blender-4.5.16-windows-x64\`.
- `engine/config.py`: `layout_backend`(기본 `blender`), `blender_exe` 경로 추가. `CINEMOKHWA_LAYOUT_BACKEND=cpu`로 이전 방식 선택 가능.
- `engine/layout3d.py`: `render_blender()` 추가, `generate()`/`stage_key()`가 backend별 캐시 분리.
- 실측: 3씬 렌더 **78초**(씬당 26초), 1280×704 PNG, 라플라시안 5~15(CPU 445 대비 30~90배 감소).
